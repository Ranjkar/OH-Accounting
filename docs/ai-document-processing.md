# AI document processing

Pipeline: `app/services/document_processing.py` orchestrates; it never
runs via Celery/Redis (in-process FastAPI `BackgroundTasks` -- a single
document's round trip is a few seconds, documented as needing a real
queue only if upload volume or multi-worker durability later requires
it).

## Pipeline stages

1. **Intake** (`document_intake.py`): content-sniffed file-type
   detection (`file_validation.py`, magic bytes, never trusts the
   client's declared MIME type), SHA-256 content hash computed up front.
2. **Extraction**:
   - Spreadsheets (xlsx/csv): deterministically parsed row-by-row
     (`spreadsheet_parser.py`) -- `classification_confidence = 1.0`
     because this is a parse, not an AI classification.
   - PDFs/images: OCR (`ocr_provider.py`, Tesseract, or a null provider
     when unavailable) extracts text, then `app/services/ai_provider.py`
     (Claude) extracts structured invoice fields from that text --
     supplier name/address/VAT, customer name/VAT, invoice/due dates,
     net/VAT/gross amounts, currency, payment terms, IBAN, credit-note
     reference, line items, and a `document_type` + classification
     confidence. Every extracted field's provenance is recorded in
     `field_sources` (not fabricated after the fact).
3. **Validation** (`validation_engine.py`): deterministic rule checks
   (missing required fields, VAT-rate/amount arithmetic consistency,
   date sanity) plus `check_business_duplicate` -- a second, business-
   level duplicate check (same supplier + invoice number + amount)
   distinct from the SHA-256 content-hash duplicate check, since two
   different scans of the same invoice won't hash-match but should still
   be caught.
4. **Status transition**: `needs_review` if any validation finding is
   an error OR confidence is below `EXTRACTION_CONFIDENCE_THRESHOLD`
   (default 0.7); otherwise `extracted` -- either way, **never
   `approved`**. Approval is a separate, explicit human action
   (`app/services/document_approval.py`, `POST /documents/{id}/approve`)
   that is the only way a document's fields become eligible to post to
   the ledger. Rejection (`POST /documents/{id}/reject`) requires a
   reason and is equally explicit.

## What's classified

`DocumentType`: `SALES_INVOICE`, `PURCHASE_INVOICE`, `CREDIT_NOTE`,
`RECEIPT`, `BANK_STATEMENT`, `OTHER`. Scoped deliberately to documents
whose fields match the `ExtractedInvoiceFields` schema (amounts, VAT,
supplier/customer) -- see "What's not supported" below.

## Confidence and human review

- `Document.classification_confidence` (0-1) gates `needs_review` as
  above.
- `ExtractedInvoiceFields.review_status` starts `"pending"` and is only
  moved forward by a human editing/confirming fields
  (`PATCH /documents/{id}/fields`) or approving the document outright.
- `field_sources` lets a reviewer see which extracted value came from
  which part of the AI's response, rather than trusting a flat list of
  numbers.

## Duplicate detection

Two independent checks, both already in place:
- **Content-level**: `Document.sha256_hash` + `is_duplicate`/
  `duplicate_of_document_id` -- the exact same file uploaded twice.
- **Business-level**: `validation_engine.check_business_duplicate` --
  same supplier + invoice number + amount from a *different* file (a
  second scan/photo of the same invoice, or the same invoice entered
  from two channels).
- **Transaction-level** (once posted): `anomaly_detection.
  detect_duplicate_invoices` (Phase 13, see
  `docs/financial-anomaly-detection.md`) -- catches a duplicate that
  slipped past both document-level checks (e.g. manually entered twice).

## What's NOT supported (by design, not an oversight)

- **Contracts, payroll documents, tax documents**: the extraction
  schema (`ExtractedInvoiceFields`) is invoice-shaped -- amounts, VAT,
  supplier/customer. Payroll documents (payslips) and tax documents (VAT
  returns, loonheffingen declarations) are *generated by this system*
  from its own ledger/payroll engines, not uploaded and OCR'd, so they
  already have their own audit trail (the `Payslip`/`VatReturn`/
  `LoonheffingenDeclaration` records and their `AuditLog` entries) without
  needing the Document pipeline. Extending OCR extraction to contracts
  would need a materially different extraction schema and was judged out
  of scope for this phase rather than half-built.
- **"Possible personal expense" flagging**: not implemented -- distinguishing
  a personal from a business expense from document content alone is
  judgment-heavy and was not built as a rule to avoid a confident-sounding
  but unreliable heuristic. Flag it manually via the existing document
  rejection/review workflow instead.
